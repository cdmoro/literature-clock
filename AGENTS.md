# Instructions for coding agents

- Read `docs/DEVELOPMENT.md` for setup and project workflows. Read the relevant feature or platform guide before changing translation/catalogue or native screensaver code.
- Keep changes focused and preserve existing user changes in the working tree.
- Treat files under `public/times/` and generated catalogue statistics as generated output. After editing quote CSV files, run `npm run generate-times`; do not hand-edit generated quote JSON.
- Organize UI translations by artifact first and feature second: `src/strings/web/<feature>.json`, `src/strings/screensaver/<feature>.json`, `src/strings/common/<feature>.json`, and future artifact folders such as `apple-app/`. Shared screensaver strings belong to the `screensaver` artifact bundle consumed by both savers; put a key in `common` only when Web and another artifact use the same key and value. Add strings for every locale supported by each consumer, and update imports, packagers, ownership mapping and CI filters when adding or moving bundles. Unknown translation paths must fail closed.
- Before adding translated UI text, search all translation JSON files for an existing key and equivalent wording. Reuse the translation when appropriate; move it to a common bundle only if multiple artifacts actually consume it, and update consumers and ownership mapping together to prevent duplicate wording from drifting.
- Before adding a translated string, search all translation JSON files for an existing equivalent key and wording. Reuse the existing translation when appropriate. If the string belongs in a different platform bundle, move it to a shared resource only when multiple consumers need it, and update each consumer and the ownership mapping together; avoid duplicate keys or locale text that can drift apart.
- `common/settings.json` key `settings_attribution_position` is also duplicated by the current macOS app in `apple/Shared/App/ClockHomeView.swift` (`WidgetQuoteDetail.detailTitle`). Include `macOS app` when assessing changes to that key. The app does not yet load this JSON directly; keep the ownership override in `scripts/component_ownership.py` in sync until it does.
- For web changes, use the relevant checks: `npm run typecheck`, `npm run test:ci`, and `npm run build`. `npm run build` creates `dist/`; do not commit generated build output unless the task explicitly requires it.
- Native screensaver builds and release version rules are documented in `screensavers/macos-native/README.md`, `screensavers/windows-native/README.md`, and the release workflow. Follow those instructions when changing native code or component versions.
- Keep the macOS and Windows screensavers at feature parity. Any screensaver feature added or changed must be implemented for both platforms, including its settings, UI text, and behavior. Review both implementations before considering the work complete. If a platform limitation prevents parity, explain it and obtain the user's explicit agreement before leaving a feature available on only one platform.
- Inspect the changed paths and estimate the user-visible scope, not just the number of files or lines changed. Use `scripts/component_ownership.py` and `scripts/validate_release_versions.py` as the source of truth for component mapping. Shared quote/translation data versions every declared consumer.
- For a clear bug fix, apply a patch bump to the affected component version. For a clear backward-compatible feature, apply a minor bump. For a breaking change, apply a major bump only when that impact is clear. If the scope or compatibility impact is ambiguous, explain the recommendation and ask before changing versions. Do not bump versions for docs/tests-only changes or unrelated internal work. `release/VERSION` is the separate consolidated release number and should change only when preparing that release.
- Do not publish, deploy, push, or create a release unless the user explicitly asks.
